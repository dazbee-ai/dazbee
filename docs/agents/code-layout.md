# Code layout

Where code goes, how the schema and tables change, the order inside each file, and the imports each folder may make. Lint checks some of these rules and `/code-review` checks the rest on every PR (see [What checks the rules](#what-checks-the-rules)).

## Adding or moving code

1. **Place it.** Pick the workspace, folder and file by [Where code lives](#where-code-lives). Search the packages below yours for a helper or type before writing one. Done when the file holds one feature, and the code sits in the lowest workspace all its users depend on.
2. **Order it.** Keep the whole file in its order: [Order inside a file](#order-inside-a-file), or its kind under [Files with their own order](#files-with-their-own-order). Done when every section of the file sits in its place in that order.
3. **Import it.** Check every import against [Imports](#imports) for its workspace. Done when each import is one its folder may make.
4. **Check it.** `pnpm lint`, `pnpm typecheck` and the unit tests of each touched workspace pass. When you moved code, madge finds no value-import cycle in each workspace you moved code in ([Import cycles](#import-cycles)), and each test runner collects as many tests as before (Tests, under [Where code lives](#where-code-lives)).
5. **Commit it.** Code moved to another file lands as a move commit, then an edit commit ([Moving code](#moving-code)). Done when each move commit holds only the changes a move may make, and the PR body names it.

## Moving code

A split, or any move of code to another file, lands in two commits:

1. **The move commit** carries the code over unchanged. It may change only imports, exports, indentation, and how a moved function reaches state it used to capture: a closure variable becomes a parameter or a dependency.
2. **The edit commit** holds every other change.

Review the move commit with:

```sh
git diff --color-moved=dimmed-zebra --color-moved-ws=allow-indentation-change <move commit>~ <move commit>
```

Moved lines show dimmed. Done when every line in full colour is one of the changes a move commit may make.

The PR body says which commits are moves.

## Where code lives

**By kind inside a file, by feature across files.** Inside a file, types, constants and functions sit in sections in a fixed order ([Order inside a file](#order-inside-a-file)). Across files, code is split by feature: a file holds one feature. A folder gets a `types.ts` only when two or more of its files share those types; otherwise a type sits in the file that uses it. Helpers, types and constants live with the feature they serve.

**Shared code moves down.** A helper or type that more than one workspace uses lives in the lowest package all its users depend on: usually `@dazbee/schema` for contract types and helpers over contract values, or `@dazbee/doc` for the layer tree and commands. It exists there once, and its users import it. Which package sits below which: [Between workspaces](#between-workspaces).

**Feature folders.** Name a folder for the feature it holds (`gestures/`, `edit-panel/`, `fonts/`), never for a kind of code (`routes/`, `services/`, `utils/`, `helpers/`, `constants/`). Two folders hold shared pieces rather than one feature: `apps/web/components/ui/` holds shared controls, and `apps/web/components/charts/` the charts and stat tiles, drawn in SVG from the chart colours in `app/styles/tokens.css`. The files directly in `apps/web/components/editor/` hold what the editor's feature folders share, such as `box-layouts.ts`, each box layout's icon and word, which the layout section, Arrange and the layers panel read. A folder stays flat until it has about 15 files; past 20, group the files that change together into a subfolder.

**Names.**

- Name files and exports after what they hold, in `GLOSSARY.md`'s terms.
- When a file no longer holds what its name says, rename it.
- Dazbee has real users (ADR-0017), so stored and wire names never change: tables and columns (see [Data](#data)), IndexedDB names, `localStorage` and `sessionStorage` keys, cookies, the service worker's cache name, the names of a stored design's records, and drag and clipboard MIME types.

**Size.**

- Keep files under 400 lines.
- Lint fails a TypeScript file with more than 500 lines of code. Blank lines and comment lines don't count, and test files count like any other. The message catalogs (`apps/web/lib/i18n/**`) and generated or vendored files are exempt.
- A file that is one deep module over the limit opens with `/* eslint-disable max-lines -- one deep module: <reason> */`. The files that open with it are the only ones that may; any other file over the limit is split.
- Split a big file only into deep modules. Each new module hides behaviour behind a small interface and passes the deletion test: if the module were deleted, its complexity would reappear in its callers.
- A big file is better than several shallow ones, meaning modules whose interface is nearly as large as what they hide.

**Tests.**

- A unit test sits next to its module and is named after it: `snap.test.ts` beside `snap.ts`.
- A test-only module, imported by tests and never by the app, is named `test-*.ts` (`test-design.ts`).
- A runner collects only the files its config matches: the `include` of the workspace's Vitest config (the packages share `src/**/*.test.ts` from `packages/config/vitest.preset.js`). A test moved outside it stops running while CI stays green. Count before and after a move, with `pnpm --filter <workspace> exec vitest list` for each touched workspace; the counts match. A move across a config's glob updates the glob.

## Data

Dazbee runs in production (ADR-0017) and keeps people's work, so every change to what is stored carries the stored data over.

- **The tables.** Change `packages/db/src/tables.ts`, or `packages/db/src/ai-tables.ts` for the AI tables, then run `pnpm --filter @dazbee/db migration <name>`. It writes the next migration into `packages/db/migrations` from every `packages/db/src/*tables.ts` file and the migrations before it, without a database; answer its questions (whether a column or table was renamed) and commit what it writes with the change. CI's `pnpm --filter @dazbee/db migration:check` fails when a tables file holds a change that no migration has. A new tables file is named `*tables.ts` and added to the schema in `packages/db/src/index.ts`. The API applies new migrations when it starts.
  - Write a migration for each change to the tables.
  - Never edit a merged migration: a database that ran it never runs it again. Correct it with a new one.
  - A migration keeps the previous commit's code working: during a deploy the new API migrates the database while the previous commit's servers still run on it. Add before you remove: a new column has a default or allows null, a table or column is removed only once no merged code reads or writes it, and nothing is renamed.
  - `packages/db/src/migrations.test.ts` applies each migration over a person, a workspace, a membership, a brand and a design (its record and stored state) written under the ones before it, and reads them back. A migration that removes one of the columns it writes changes its rows in the same PR.
- **The design schema.** Change it in `packages/schema` and in everything that writes it. A change after which a stored design would not open, or would open wrongly, raises `SCHEMA_VERSION` and comes with the step that carries stored designs over to the new version.
- **Carry-over steps.** Add the step to `STEPS` in `packages/schema/src/carry-over.ts`, naming the version it carries to, with a test in `carry-over.test.ts` that reads a layer as it was stored before. A design's document holds no version, so a step finds what it carries over in the layer record itself and gives back the same object for any other record. Steps run wherever stored layers are read, never written back: `parseLayer` (every read of a design or a version), `parseDesign` (templates, exports and designs made from content), the sync server's checks of a change set, and the clipboard. A layer that still holds an older value keeps it until a command writes that value again.
- **The schema version.** `SCHEMA_VERSION` in `packages/schema` names the design schema's version. The API writes it into the design's record (`designs.schema_version`) when it creates a design, and every sync token for the design carries it, signed. A tab sends the version it was built with when it connects, and the sync server refuses a tab older than its token's version, or one that sends no whole number from 1, when it connects and at each token renewal (close code `tabTooOld` in `packages/schema`'s `SYNC_CLOSE`); the tab then shows "Reload to update". The design's document holds no version, so nothing a tab writes decides who may connect. Raise the version with a change that a tab built before it would write wrongly, or that stored designs must be carried over for.
- **The reset.** `docker compose down -v`, then `docker compose up -d`, recreates the local databases and storage, and the API applies every migration from the first. It only clears a developer's own data; it is never how a change reaches a database that keeps people's work. CI starts fresh on every run.

## Order inside a file

Every TypeScript file follows this order, except the kinds under Files with their own order:

1. The directive (`'use client'`), if any.
2. A header comment saying what the module does, when the file name doesn't say it.
3. Imports, in these groups. `eslint --fix` puts them in the groups and sorts each group (`eslint-plugin-simple-import-sort`).
   1. Side-effect imports (`import 'server-only'`, `import './globals.css'`). They keep their order among themselves.
   2. `node:` built-ins.
   3. npm packages.
   4. `@dazbee/*`.
   5. `@/` (only in `apps/web`).
   6. `./` (and `../` outside `apps/web`).
4. Exported types and interfaces.
5. Private types.
6. Constants: exported ones first, then private ones.
7. Module state (`let` variables, caches, listener sets), if the module has any.
8. Exported functions, with the main one first.
9. Private helpers, in the order the code above first uses them.

**Declare before use.** Everything is declared above its first use, except a function declaration (`function name() {}`), which a function body may call from above it. So a private helper that sits below its first use is a function declaration, and a const arrow function, a constant, a class or a type (type references count) sits above its first use. `@typescript-eslint/no-use-before-define` checks this.

Two types that refer to each other are the one exception: above the line in the first type that names the second, put `// eslint-disable-next-line @typescript-eslint/no-use-before-define -- the types refer to each other`. Nothing else disables `no-use-before-define` or `max-lines`, apart from the one override under Size.

A table built while the module loads keeps its helpers above it, because they must exist when the table is built.

## Files with their own order

These orders replace the main one for their kind of file.

**React component files:**

1. The directive.
2. The header comment.
3. Imports.
4. Exported types.
5. Private types.
6. Constants.
7. Private pure helpers (no hooks, no JSX).
8. Hooks: exported ones, then private ones.
9. The exported component or components, with the main one first.
10. Private components, in the order the main one renders them. They sit below their first use, so each is a function declaration.

**Schema files** (`packages/schema`):

- Each zod schema is followed by its type: `export type X = z.infer<typeof X>`.
- A building block that only one schema uses sits directly above that schema.
- Functions come after all the schemas.

**Factory modules.** A factory module is a function that owns state and returns an interface, such as `exportClient`. Inside the function:

1. The dependencies it is given.
2. Its state, each piece with a one-line comment.
3. What it creates and must free.
4. Queries, then the functions that change its state or the design.
5. Listener wiring.
6. The returned object. Each member is one line that points to a named function, and `destroy()` comes last, freeing things in reverse order of creation.

**Unit test files:**

1. Fixtures.
2. One `describe` per export, in the order the module declares its exports.

## Imports

### Between workspaces

Import another workspace by its package name (`@dazbee/doc`), declared in the importing workspace's `package.json`. Packages depend only downward, schema → doc → renderer → editor, and never on an app (ADR-0001). `pnpm lint:deps` checks the declared dependencies, and the ADR-0001 pattern in the shared ESLint preset fails a relative import into another workspace.

### In `apps/web`

- `@/` points at the app's root, `apps/web/`.
- An import of a file outside its own folder uses `@/` (`@/lib/i18n`). An import of a sibling uses `./`.
- Lint fails `../` imports and relative imports into a subfolder (`./x/y`). So every import between folders reads `@/<folder>/…`, and the table below is checked from the import's text.

Each folder may import only what this table lists, plus npm packages and `@dazbee/*`. `no-restricted-imports` checks it.

### In `packages/doc`

- Nothing under `commands/` imports what keeps the store (`client-store.ts`, `plain-store.ts`): a command reads and writes through the store (`store.ts`) only. `no-restricted-imports` checks it; test files are exempt.

### In `packages/editor`

- Imports follow the build order under [The editor package](#the-editor-package): a module imports only modules built before it.

### Import rules in ESLint configs

In flat config, a later `no-restricted-imports` entry replaces an earlier one for the same files; the options don't merge. So every config block that sets `no-restricted-imports` lists the preset's exported `adr0001Pattern` among its `patterns`, beside its own. In `apps/web` it also keeps the app's `../` and subfolder ban. `pnpm lint:deps` (`dazbee-check-deps`) loads each workspace's ESLint config and fails on a block that lacks them.

### Import cycles

No workspace has a value-import cycle, and a change adds none. A cycle made only of type imports does nothing at runtime, so it is allowed. Check each workspace you moved code in, from the repo root, so madge reads the repo's `.madgerc` (which skips type-only imports):

```sh
pnpm dlx madge --circular --extensions ts,tsx <source folder>
```

For `apps/web`, run `pnpm dlx madge --circular --extensions ts,tsx --ts-config tsconfig.json app components lib scripts` inside `apps/web`, because madge resolves `@/` imports from the folder it runs in; it still finds the root `.madgerc`.

`canvas/overlay` owns no state: it draws from what the modules above own, in a fixed order. `gestures/double-click` owns none either: it acts through the modules and the pointer's functions it is given.

- **Core and shell.** A core file decides what the design, the selection, the camera or the tool becomes, and compiles and runs in Node; a shell file is what only a browser can run. A **stage point** is a point in CSS pixels from the top left of the canvas element; the view speaks in stage points, and the surface turns a client point into one. The **redraw pass** (`canvas/redraw`) is the work the draw loop does each time it runs, apart from putting pixels on the screen and building the overlay's elements: in a browser the surface's animation-frame callback runs it with its `paint`, and with no `paint` it runs to its end. `core.ts` and every file it imports are the core, and the compiler checks it: `packages/editor/tsconfig.core.json` compiles them with no browser's and no Node's types, so a browser global or type in a core file, or a core file's import of a shell file, fails `pnpm typecheck`. The few globals a core file may use are declared in `core-globals.d.ts`, each with what it is for; adding one there is a decision a review sees. A core module never reads the time or the screen's animation frames itself: `CoreStart` gives it `after`, which runs a callback after a pause, and `motion`, the screen's animation frames and the system's reduced motion, which the camera's glide steps on; `editor.ts` and `viewer.ts` give both, and without them a pause never ends on its own and a glide moves straight to its end. `EditorCore` (`core-interface.ts`) is the open core, and neither it nor `Editor` extends the other: both extend `EditorBase`, the members that mean the same without the page and with it, and each declares beside it only its own and the members that take or give a point. Every point an `EditorCore` member takes or gives is a stage point, and `editor.ts` turns the client points `Editor`'s members take into them.
- **Where a new module goes.** A module that decides what the design, the selection, the camera or the tool becomes is the core's: `core.ts` builds it at its place in the table's order, and it takes inputs, payloads and the functions it is given, never an element, an event or a browser global. A module that reads or builds the page (elements, events, the system clipboard, storage, a worker, the network) is the shell's: `editor.ts` builds it on the core's modules (and `viewer.ts` on its own core's, for those a viewed version uses), and its file is added to `SHELL_FILES` in `packages/editor/eslint.config.js`. A member the app needs whose work needs no shell module is declared once, in `EditorBase`, and built in `core.ts`'s `shared`, which `editor.ts` spreads into the `Editor`. One that takes or gives a point is declared in both: in `EditorCore` with a stage point and in `Editor` with a client point, which `editor.ts` turns into the stage point. One whose work needs a shell module is `Editor`'s alone. `editor-interface.test.ts` names the members each declares beside the base's, and a test of a core member opens the core with `test-editor`.
- **The agent tab.** `agent-tab.ts` (`@dazbee/editor/agent-tab`) opens the core in Node for an agent (ADR-0019), as `editor.ts` opens it in a browser but with no shell module: on `open-tab`'s tab, with a stage of no size and no tab copies. Its presence is where the agent last worked, which the MCP tools hand it (`show`): `agent-presence` works out what a step changed and the presence that shows it, and makes the agent's note fit to send. It is neither a core file nor a shell file: it opens the tab, so it is not in `tsconfig.core.json`'s files, and it reads no browser global, so it is not in `SHELL_FILES`. Its session ends each step with what `layer-edits` fits after the page's edits (the texts whose words or sizing changed, `SIZES_TEXT`, and the groups around what changed), so an agent's commands are fitted as a person's are.
- **Pointer and key inputs.** A **pointer input** is one pointer event of the canvas and a **key input** one key event of the window, as plain data with the names the browser's events give the same things (`gestures/inputs`); a pointer input's place is a stage point, and a key input carries what the page says about where the key was pressed (its `target`). `gestures/dom-input` makes them, the only module that listens to the canvas's pointer events and the window's keys, and does what the editor answers: it keeps the browser from an input that was the editor's alone, then throws on what the action of the editor's own key threw, and captures the pointer when a press asked `gestures/hold` for it. A core module never reads a DOM event, an element or the computer's platform: it reads an input, or asks a function it is given (`hold`, `onMac`). The cursor is `gestures/stage-cursor`'s to decide, which the pointer builds and answers for (`cursor()`, `onCursor`), and `gestures/dom-input`'s to show.
- **Clipboard payloads and remembered values.** A **clipboard payload** is what a copy or a cut puts on the clipboard, or a paste brings from it, as plain data (`clipboard`): plain text, the editor's own types by name, and files, each named and typed at once and read only when asked. `place` gives one for a copy and a cut and takes one for a paste, answering at once whether it took it, and `text/typing` does the same for the text being edited. `clipboard-events` is the only module that listens to the window's clipboard events and the only one that writes to the system clipboard. The **remembered values** are what the editor keeps on a device between designs and visits, the last copy and the copied style: `clipboard` reads and writes them through the service it is given (`get`, `set`), which `editor.ts` makes from the browser's storage and a test from a map. A core module never reads a clipboard event or the browser's storage, and never fetches: the fonts the app ships are fetched by `vendor` for `editor.ts` and `viewer.ts`, and handed in as bytes.
- **What a behaviour shows is data.** A behaviour that shows something over the stage gives it from `shown()` as plain data (`gestures/drawing/drawing`, `gestures/pen/pen`, `gestures/crop/cropping`, `text/typing`, `gestures/select/{auto-layout-drag transform-drag radius-drag}`, `gestures/guides/guide-drag`, `gestures/colour-pick`), and a `*-parts.ts` file beside it builds the overlay's elements from that; one that places a box in a frame takes the overlay's `placeBox` or `outline`. The picked frame's handles are drawn as the selection's are, on the frame `gestures/select/frame-resize`'s `handled()` gives. A behaviour module never builds an element, and never imports from a parts file.

- **Faults.** Only `faults` handles a `CommandFault` (ADR-0004). The session tells its fault listeners of a fault once it is at rest, with the fault's step put back, and `faults` is that listener, so a fault is handled once, wherever the command was run: the command's name and cause are logged, the drag held is dropped as Escape drops it, typing stops and the pen's path ends, and the page is told with the `notApplied` notice.
- **View only.** A Reviewer's session refuses every write (C35); only `view-only` hears its refusals. Once the refused call is over, it ends what is open on the stage as a fault does and tells the page `viewOnly`, once until the tab can edit again. Every member the page or the browser calls goes through its `guard` in `core.ts`, and the page's `session` is its `pageSession`, so a refusal never reaches the page. A write that only follows another (a group fitting its layers again) is not tried in a read-only session. The core also starts nothing that only leads to a write: `tools` keeps only `VIEW_TOOLS` (Select and Hand), a double click opens no crop, path edit or frame rename, and a tab turning read-only ends a drawing tool, a crop and a path edit, and puts back a drag held, telling the page `nowViewOnly` when the drag had written and the link has not ended (`TabAccess.quiet`): its changes were not kept, as the server's `viewOnly` rejection of a step that ended says. `EditorBase` tells the page whether the tab may only view (`readOnly`, `onAccess`), and `tellViewOnly` says View only, under the same once-rule, for what the page turns away before it reaches a command (a dropped file). In the web app the stage reads it with `useReadOnly` and hands it down with `view-only.tsx`'s `ViewOnlyProvider`; each surface reads `useViewOnly`. A menu keeps an action only if `viewAction` (`shortcuts.ts`) says it only looks, selects, copies or moves the view, the edit panel leaves out the controls `ONLY_ACTS` (`edit-panel/tabs/tabs.ts`) names, and a panel's or pop-up's body sits in a `ViewOnlyFieldset`, which turns its controls off; a pointer-only control (a knob's scrub, a gradient's stops, a reorderable list) checks `useViewOnly` itself.
- **The gesture lifecycle.** `gestures/pointer` routes pointer events to the behaviour that owns the gesture. Each behaviour module calls `beginGesture` and its step's `end` (ADR-0004), keeping the step on the drag it starts. A move with Alt (`gestures/select/move-drag`) cancels its own step and begins another each time Alt changes, so the drag is still one undo step. A drag in a flow (`gestures/select/auto-layout-drag`) does the same each time Alt changes, each time the pointer leaves its box, and each time it comes back to the place the press found the layers in; a drag the browser takes away (`cancelDrag`) cancels its step too, so its release drops nothing. One exception: `gestures/drawing/drawing` begins the step that makes a text box, and `text/typing` ends it when typing stops or pauses once the box holds a word, so the new box and its first words are one undo step. Escape mid-drag is `gestures/pointer`'s, which `gestures/dom-input` asks before the page's chrome hears the key: it drops the drag without its end and calls `cancel` on the drag's own step, which puts back all that step wrote and leaves no undo step, then puts back the selection the press found. The pointer's `dropDrag` also ends a release whose copies are each where their originals are: the drag leaves no copy and no undo step, and the selection is the one `copiesUnmoved` gives, the originals' as it was when the copies were made.
- **Late binding** is allowed only for:
  - `view.redraw`, which state owners call when they change;
  - the redraw pass's `shownChanged`, which `selection`, the behaviours and `gestures/pointer` call when what they show changes;
  - the animation-frame callback `draw()` of `editor.ts`, and of `viewer.ts`, which `canvas/surface` receives when it is built and calls from its animation-frame schedule;
  - `tools`' `finish` and `changed`, which end the pen's path and show the pointer's cursor when the tool changes;
  - `faults`' `endOpen`, which drops the pointer's drag and settles typing and the pen's path when a command faults;
  - `view-only`'s `endOpen`, the same call, when a Reviewer's write is refused;
  - `restore`'s `endOpen`, which ends the pen's path, the drag and typing as they end before Undo;
  - `gestures/pan`'s `showCursor`, which shows the stage's cursor as a pan starts and ends;
  - `gestures/held-keys`' `keysChanged`, which tells the move or the reorder held Alt and shows the stage's cursor as a key or the focus changes the deep key or Alt;
  - `open-tab`'s recompute and font hook, which the tab is opened without and `bind` gives it from the core once it is built: until then a follow-up waits (D6);
  - `canvas/view`'s `composition`, through which the frames' pictures read the text layer `text/typing`'s composition draws, and its count.

  In `core.ts`, each late-bound call is a function declaration below the module it calls (`shownChanged`, `showCursor`, `finishPath`, `endOpenOnStage`, `endOpenAsUndo`, `composition`), so it is declared before use; `draw` is one in `editor.ts` and in `viewer.ts`.

- **The CPU surface.** `canvas/thumbnails` and the export code draw on the CPU surface, so they never receive `gl` or the WebGL surface (ADR-0005). They read a frame's `scene` or `render` it without options, never the shown scene, so the hidden layers the stage shows are drawn only there.

## Keeping the editor fast

The editor reuses work between redraws by object identity: a layer that didn't change is the same object in the next design, so its scene, auto layout, text layout and recorded picture are kept. Code that runs often keeps that true.

1. **Per pointer move or per redraw, read layouts through the scene memo:** `scenes.scene(frame)`, `scenes.laidOut` or `boxes.boxIn`. Never call `render()` without the memo there.
2. **Call `render()` without the memo only inside a one-off action**, such as a click, a key or a menu pick.
3. **Write only what changes.** A command that sets a value a layer already has still replaces the layer object, which drops its cached scene, layout and picture.
4. **Never change a layer object in place.** The caches rely on an unchanged layer being the same object.
5. **Panels read the design through `useLiveDesign`**, with `'held places'` unless they show a layer's x, y, width or height, and work that can wait runs through `afterDraws`, so a drag doesn't re-render React on every move.
6. **Exports and thumbnails draw on the CPU surface**, and exports run in the export worker (ADR-0005).
7. **The screen draws images from display copies** no bigger than it shows them, which the image worker decodes and shrinks; never decode an image with `MakeImageFromEncoded` on the main thread for the screen. The copies hold at most `COPIES_BUDGET`; past it the ones drawn longest ago, never one the shown page draws, are let go.

# Every export is drawn on the CPU surface

Formats were replaced by frames on 2026-11-04 (ADR-0014), so the resolution below is the frame's; the rest stands. Curved and bounced text reaches a PDF as shapes, not text (ADR-0021).

One renderer (CanvasKit, our own build in `packages/canvaskit`) draws both in the browser and in Node. The editor screen uses the WebGL surface for speed, but every PNG, JPG and WebP export, in the browser and on the server, uses the CPU surface, because GPU and CPU anti-alias edges differently and only CPU drawing gives identical pixels everywhere. Fonts and images are decoded by CanvasKit from bytes we control, never by the system or the browser. The export parity pass mark is 0 differing pixels: any tolerance would hide real bugs.

## Consequences

Every runtime loads the same build, because two builds could draw differently. It is npm's `canvaskit-wasm` 0.42.0 `full` build (JPEG and WebP encode, paragraph and HarfBuzz) made from the same Skia commit, `66108990f8f6edbfe9650d7023b5cf1154d71910`, plus Skia's PDF and SVG backends, which npm's builds leave out. `build/vector_bindings.cpp` hands out a CanvasKit `Canvas` for each PDF page and SVG document, so PDF and SVG exports run the same drawing code as the pixels. The wasm is 9.5 MB (3.74 MB gzipped) against 8.2 MB (3.29 MB) for npm's full build.

The build runs in CI (`.github/workflows/canvaskit.yml`, about 15 minutes) and is published as the GitHub release `canvaskit-<recipe hash>`, where the hash covers everything in `packages/canvaskit/build`. `packages/canvaskit/release.json` names that release and each file's SHA-256, and `pnpm install` fetches and checks the files, so no install or normal CI run rebuilds. To update the build, for example to a newer Skia, change `build/` (the Skia commit is in `build/skia-commit`), let the workflow build it on the pull request, commit the `release.json` it prints, then re-measure the drift baselines. Its types are npm's 0.42.0 types, copied into `types/canvaskit.d.ts`, plus the PDF and SVG documents in `types/index.d.ts`; a newer Skia means copying the matching types.

PDF and SVG exports (#56) draw the same scene with the same code onto Skia's PDF and SVG canvases, so shapes and text stay vectors. What the file can't hold is drawn on the CPU surface at the format's own resolution and placed as an image: in a PDF a background blur, in an SVG layers with opacity, effects, masks, angular gradients or image fills, and blend modes. A PDF keeps text as text with its fonts embedded (a variable font's glyphs go in as shapes, Type3, one font for each weight drawn, and the text still reads back); an SVG draws it as shapes. They can't be pixel-identical to the CPU render, since another app draws them, so each fixture's share of differing pixels, drawn by pdfium and resvg, is recorded and checked (`tests/pixels/reference/vector-baselines.json`).

Images export at a scale of 1x, 2x or 3x (#604): the canvas is scaled before the scene is drawn on a surface that many times the frame's size, so text, paths, blurs and shadows are drawn at that density, not enlarged, and the parity mark holds at every scale. WebP comes from the same build's encoder, at a quality from 1 to 100; 100 is lossless. An image export is at most 16,383 pixels a side, the most WebP holds, kept for every type so a frame exports the same in each, and 50 million pixels, so a tab's export worker doesn't run out of memory. CanvasKit's wasm memory grows to fit the biggest surface drawn and never shrinks, so the browser ends its export worker after a frame past 20 million pixels, and the next export starts a fresh one.

The editor screen can drift slightly from the export. The spike measures how far; if it's visible, a "preview as exported" mode draws the CPU version in a worker.

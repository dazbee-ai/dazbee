# Uploads go straight to storage by signed URL; originals are stored once per workspace by content hash

`packages/storage` talks the S3 API with aws4fetch: Cloudflare R2 when deployed, RustFS in Docker Compose locally and in CI (MinIO no longer publishes images). The browser sends a file to the web app's server, which hashes it, asks the API for an upload, and PUTs the bytes to a signed URL that is good for five minutes, one key, one content type and one size (`apps/web/lib/server/api.ts`); the browser never reaches storage. The API then records the asset after hashing the stored bytes and reading the image header; bytes that don't match their hash or aren't a PNG, JPEG or WebP are deleted and refused. Originals live at `workspaces/<workspace>/originals/<sha256>`, so the same file is stored once per workspace, and every brand that uploads it gets its own asset row, so assets never cross brands. (They were under `orgs/<org>/` until ADR-0011.)

Reads go through the API too: it signs a short-lived GET URL after the workspace and brand checks, and the web app passes the bytes on to the editor, so browsers never hold storage addresses or credentials. The editor and Node renders load the same bytes by asset id and decode them with CanvasKit, so an image renders identically in both. Resized copies, when we need them, are images we make and store as their own objects; nothing is resized on the fly.

A picture an agent adds from an outside link starts on the API instead: the API fetches it through its one safe fetch (`apps/api/src/fetch/safe-fetch.ts`: https only, public addresses only with the connection made to the address it checked, at most three redirects each checked again, a cap on the decoded bytes, a time limit, no credentials), stores the bytes under the same key by their hash, and records the asset with the same checks as an upload, so no signed URL is needed. Every other feature that fetches from an outside link uses the same safe fetch.

A file on the machine an agent runs on comes in through an **upload link** (`upload_image`). The API makes a one-time link, `https://app.dazbee.com/uploads/<token>`, for one brand, one type and one name, working for 10 minutes, and keeps only its token's SHA-256, in `upload_links`. The agent PUTs the file to it; Caddy sends only a PUT on that path to the API, its body capped at the upload limit. The API checks the link (known, unused, unexpired, its member and agent access still editing the brand), spends it, reads the body up to the type's limit, checks the bytes are a picture of the link's type, of at most 25 megapixels as a picture from a link is, and stores and records them with the same checks as an upload, in the one place for a picture from outside. The link reads nothing and opens no other route. It is a table row rather than a signed token because one use needs a record that both of the API's colours share and a restart keeps; a signed token can't be spent. It goes to the API rather than to a signed storage URL, which would hand the agent the storage address and leave the bytes unchecked until a second call recorded them.
